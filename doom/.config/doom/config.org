*** Vulpea
Vulpea owns the note index. Each note is an ordinary Org file or heading with
an =ID=; filenames reuse that ID. Aliases use Vulpea's =ALIASES= property.
The database is separate from the notes and can be rebuilt with =SPC v u=.
This library uses =vulpea/icloud-org.db= and =vulpios-export-icloud-org/= under
local Doom data, preserving the previous library's database and exporter state.

After changing packages or modules, run =doom sync= and restart Emacs so the
previous ID advice and note integrations are unloaded. New library folders are
created only by the explicit initializer; journal files are created when requesting
an absent day. =SPC v d= checks the resulting setup.

Vulpios can browse the library on iOS using metadata published through the public
Vulpea API. Doom loads the Vulpios companion directly and restores automatic
export from the local enabled marker. To opt in on the designated Mac, verify
that =org-directory= and the active Vulpea database describe the same library,
then run =M-x vulpios-export-enable=. It publishes =.vulpios/catalog.json= inside
the library and refreshes it after Vulpea index updates.
=M-x vulpios-export-disable= stops publication. The
activation marker and writer identity stay in local Doom data; the live SQLite
database is never copied into iCloud. Only enable one Mac for a given library.
The exporter reads indexed metadata, not note bodies or attachment contents.

#+begin_src emacs-lisp
(use-package! vulpea
  :after org
  :demand t
  :init
  (setq vulpea-db-sync-directories (list org-directory)
        vulpea-default-notes-directory org-directory
        vulpea-db-location (expand-file-name "vulpea/icloud-org.db" doom-data-dir)
        vulpea-create-default-template
        '(:file-name "${id}--${slug}.org"
          :tags ("inbox")
          :properties (("CREATED" . "%<[%Y-%m-%d %a]>"))))
  :config
  (require 'mho-vulpea-workflow)
  ;; The companion is optional; missing checkout or invalid opt-in must not
  ;; stop ordinary Vulpea indexing. Identity and enablement remain local.
  (mho-vulpea-workflow-start-exporter
   (expand-file-name "vulpios-export-icloud-org/" doom-data-dir))
  (setq vulpios-export-use-catalog-changes t)
  (vulpea-db-autosync-mode +1))
#+end_src

*** Vulpea PARA
PARA classifies notes by their role. Areas are file-level notes tagged =area=;
projects are headings tagged =project= inside an area. Live file-level notes
are resources without needing another tag; areas and resources can overlap.
Project commands retain =PROJ= and
reconcile =CLOSED= when child work changes. Guarded archival adds =ARCHIVE= in
place only after all child work is complete and clocks are closed; older
Archive subtrees remain readable.

Start with Work, Home, Writing & Website, and Stillvaro. Work and Home retain
=work.org= and =home.org= so the existing capture keys keep working. Other
areas use UUID filenames. Every area created with =SPC v P A= is explicitly
=private= and has =Notes=, =Tasks=, and =Archive= headings. These headings have
UUIDs for database-backed refiling. Work and Home also have =Inbox=, =Actions=,
and =Meetings= for their existing captures. Their project capture keys now
target =Tasks=, matching PARA. Journals continue in =journal/= without converting historical files.

| Key       | Action                                      |
|-----------+---------------------------------------------|
| SPC v P A | Create a private area                       |
| SPC v P p | Capture a project in a selected area         |
| SPC v P a | Find an area                                |
| SPC v P f | Find a project                              |
| SPC v P r | Find a resource                             |
| SPC v P g | Open Strategic Overview                     |
| SPC v P G | Show tasks for one area                     |
| SPC v P x | Archive a project within its area           |
| SPC v P d | Check PARA consistency                      |
| SPC v P b | Backfill agenda tags after importing notes  |

=org-capture= key =p= also creates a project. It uses =PROJ= and a readable
=Area > Project= category; finish capture with =C-c C-c=. Give the project a
clear outcome, then add =NEXT= or =TODO= tasks beneath it. =project= does not
inherit to subtasks, so a task is not mistaken for another project.

Save notes before opening the agenda or refiling. PARA maintains the =agenda=
file tag automatically, and the existing Strategic Overview queries those
files. Work and Home always remain in the agenda for inbox review. Database
checks recognize both =DONE= and =XOUT= as finished. Other custom task states
remain unchanged. Archived and commented tasks do not keep an area active;
the local integration corrects this behavior in the pinned upstream version.
The upstream default agenda blocks are not installed.

=C-c C-w= refiles to live indexed notes/headings by title. Public files are
excluded as task destinations. On an existing heading, =SPC v h= creates an ID
so it becomes available after saving. Use =SPC v P x= for guarded project archival; the PARA command delegates to
the same guard. The ordinary Org archive command remains available for other
Org content and retains the existing external archive path.

Keep planning areas private. Link projects to separate resource or draft files,
and add =public= plus =blog=, =weeknote=, or =page= only to the notes prepared for
the website. During weekly review, process inboxes, choose next actions, extract
reusable notes from the journal, and archive completed projects.

The package is pinned in =packages.el=. Its pieces are configured individually
so =vulpea-para-setup-defaults= cannot replace the existing agenda and captures.

*** Vulpea Journal
Existing daily, monthly, and custom dated journals are resolved from saved
source before creating a day. Duplicate dates and unsaved journal buffers stop
creation with an explanation. New days use monthly files grouped by ISO week,
newest first, with a minimal Tasks section. Existing plain monthly layouts and
historical daily files are retained; nothing is migrated on setup.

=SPC v T f/r/w= starts an optional private Focus, Reflection, or Weekly review
entry. =M-x mho-vulpea-journal-capture= also accepts a selected date. A journal

*** Website
The local publisher builds =mholson.com= from Vulpea's saved notes using
[[https://github.com/d12frosted/publicatorg][Publicatorg]] and the local Nordic Archive theme. Publicatorg compiles the
sanitized public page snapshots; the source-selection, journal privacy and
manifest protections remain in the local publisher. Publicatorg and its Org-ML
dependency are pinned in =packages.el=; install them with the normal =doom sync=
workflow.

The design uses a simple introduction, dated writing, compact project links,
and a single-column reading page. Longer articles receive a collapsed contents
list; short pages do not need one. Light and dark appearances use the Nordic
palette. A small =feed.xml= RSS feed lets readers follow public writing and
weeknotes without adding accounts, scripts or a newsletter service.

| Key       | Action                                         |
|-----------+------------------------------------------------|
| SPC v p n | Create a public page, blog post, or weeknote     |
| SPC v p b | Build the local preview                        |
| SPC v p p | Build and open the preview in your browser      |
| SPC v p e | Build and export to =~/GitHub/mholson/=          |

Save a note before building. For notes added outside Emacs, use =SPC v u= to
refresh Vulpea first. Add =public= with =SPC v t a= to publish an existing
file-level note. Ordinary inbox notes stay private. Use the tag =blog= for
Writing, =weeknote= for Weeknotes, and =page= for Pages (the default).
=#+date:= controls ordering and =#+description:= supplies an optional summary.

Ordinary notes must have an explicit file-level =public= tag. A file tagged
=private= or =noexport= is excluded even if it also has =public=. Those tags,
and =COMMENT= headings, exclude subtrees. Links and backlinks use only the
remaining public content; links to unpublished notes become plain text.
Public URLs normally use =notes/ID.html=, so changing a title or filename does
not break them. Selected product and documentation notes have stable root routes
in =mho-vulpea-site-page-routes=. Those mappings never make a private note public. Heading IDs receive stable anchors. Relative image/PDF links are copied
only from inside the library.

Journal containers use =:journal:= without a file-level =private= tag: this
keeps the container unpublished while permitting individual entries to opt in.
An explicit file-level =private= or =noexport= still protects every entry.
Vulpios gives new entries their own =private= tag; making an entry Public
replaces only that tag with =public=. The publisher requires its own ID and
=public= tag, and exports only that entry's subtree, title, description, and
creation date. Private, noexport, COMMENT, and archived ancestors prevent an
entry from being selected. Neither unmarked siblings nor calendar context are
included. Legacy =public= tags on journal files never publish the whole file.
A file under =journal/= without a journal tag also cannot publish as a whole.

Monthly entries must be direct children of validated day headings; daily
entries must be at the root or directly under Work, Personal, or Weekend.
Week/day/Tasks containers and task subtrees are not entry pages. Ambiguous IDs,
metadata, malformed file aliases, or unfinished structure stop publication of
ordinary notes and journal entries rather than guessing. Journal dates and
calendar grouping must also be unambiguous. Entry pages appear in Writing, or Weeknotes with an own
=weeknote= tag. Their retained child IDs become anchors, and links to the
journal filename remain unpublished. Use entry ID links instead.

Public/Private controls publication eligibility. They do not deploy changes or
immediately remove an already deployed page; rebuild, export, review, and
publish the website to apply a change to the live site.

The build does not evaluate source blocks or macros, follow =INCLUDE= or
=SETUPFILE=, or use per-note export settings. Keep content to publish directly
in the note. Custom HTML is treated as authored public content. The generated
site uses Org's standard HTML body. Every build uses a fresh staging directory,
validates the saved public sources again, and lets Publicatorg compile the
rendered note pages before replacing the completed preview. Publicatorg's
automatic database sync is disabled for this already-selected snapshot; finish
the normal Vulpea index refresh before building. LaTeX math is rendered to native MathML with the installed =pandoc=
(in sandbox mode), so published pages do not need a math CDN or JavaScript.

Preview builds go into Doom's cache. Export updates only the publisher's
manifest-owned output in the website checkout. Its first export replaces the
four archive pages. The Stillvaro rebuild explicitly adopts =mho-0002.html=
when its Org draft becomes public; its guides use =stillvaro-*.html=. Existing
assets, =CNAME=, and =.nojekyll= are retained. A mapped product route never falls
back to a stale checkout copy when its source is private. Removing =public= removes that generated page on the next export.
Review the website Git diff and use the website's normal Git publishing process
after export. No command here commits, pushes, or changes hosting settings.

Website sources live in =01 Projects/Website/=. The website new-note command
uses this folder through =mho-vulpea-site-notes-directory=. Stillvaro's six
pages share one Org file, with local screenshots in =stillvaro-media/=.
The =product= tag selects the visual
product layout; =documentation= keeps supporting guides out of the homepage
collections. Both still require =public=. Keep the legacy =support=,
=privacy-policy=, and =terms-of-use= anchors for links from the app. Screens
marked Preview describe newer source work, not confirmed App Store availability.

To inspect the design with clearly labeled sample content, run
=emacs --batch -Q -l src/vulpea-site/preview.el= from this config directory.
It prints a local HTML path and keeps its notes and database in a temporary
directory. The real library and website checkout are not modified. Normal
builds never include the sample notes or preview banner.

** New-library bootstrap
=M-x mho-vulpea-library-preview= shows a generated, private Work/Home starter
with linked review resources. =M-x mho-vulpea-library-initialize= writes only
an absent or empty folder, refuses all existing content including hidden files,
and does not switch =org-directory=, enable an exporter, or migrate any notes.
Choose the new folder in Vulpios and update the desktop library configuration
only when ready. The declarative profile is saved as
=.vulpios/template-profile.json= and contains no executable Lisp.
